From a note
to useful context.

A practical guide to the memory layer: what to record, how to retrieve it, and where your agent takes over.

Verified against main 708c973 · Python 3.9+

Start with one fact.

Install the project from its repository in your Python environment. These instructions do not assume the similarly named registry package is this project.

python -m pip install "git+https://github.com/LuigiFerronatto/TESSERA.git"

Run this in the project where you want to keep memory. The explicit memory-only policy selects the generated memory folder as the source.

tessera init --project . --store memories --sources memory-only --non-interactive

tessera write --id project/database --type factual --episode setup --content "The project uses PostgreSQL as its primary database." --tags database,postgresql

tessera index
tessera query "what database does the project use?"

The fact is stored as Markdown. Indexing makes it retrievable. The query returns evidence for the consuming agent to interpret.

Source: Repository quickstart

Three types of memory.

The drawers describe the role of a note. They are semantic categories, not three databases or mandatory folder names.

Facts factual

Concrete observations or recorded information. For example, “The project uses PostgreSQL.” A factual type does not establish truth or authority.

Preferences preference

Someone’s tastes, desired behavior, feedback or corrections. For example, “Give me the summary before the implementation details.” Earlier and later preferences can remain relevant in different contexts.

Insights procedural_anchor

Lessons and procedures that can transfer to another task. For example, “Check whether port 5432 is free before starting the database.” A procedural anchor is memory that can guide action; it does not execute a procedure.

The Python convenience writers choose the corresponding type for you:

from tessera import TesseraEngine

engine = TesseraEngine(storage_dir="./memories")
engine.write_fact(
    mem_id="project/database", episode_id="setup",
    content="The project uses PostgreSQL.",
)
engine.write_preference(
    mem_id="team/report-style", episode_id="feedback",
    content="The team prefers a short summary before technical details.",
)
engine.write_insight(
    mem_id="operations/database-start", episode_id="deployment",
    content="Check whether port 5432 is free before starting the database.",
)
engine.build_index()

results = engine.retrieve_context(
    "What should I check before starting the database?",
    top_n=3,
)

These are writes: the example creates three notes. Choose distinct memory IDs for distinct notes.

Books, notebook, catalog.

Sources sources.roots
The Markdown documents explicitly selected for reading and indexing. Indexing does not rewrite source text.
Memory folder store.path
Where new memories are written. Include it among the source roots if you want those notes in the index.
Derived index index.path
The rebuildable search state. In a project configuration, keep it separate from the writable memory folder.

To inspect a broader source selection before applying it, run:

tessera init --project . --store memories --sources recommended --dry-run

The project configuration records the selected source policy. Existing files in an arbitrary memory folder are not implicitly selected merely because of the folder’s name. A direct Python storage_dir example remains store-only; project-wide source selection uses a resolved configuration.

Read the evidence, not just the score.

TesseraEngine.retrieve_context() returns a list of structured hits. These are the fields you will usually inspect first.

id and related_ids
The memory identity and its directly connected memory neighbors.
relevant_evidence and body
A query-specific excerpt, alongside the original memory body. The excerpt can be null if the lexical support threshold is not met.
score and score_explain
Relevance and its component signals. Neither is a truth, authority or temporal-validity score.
provenance and evidence
Document-level and query-specific evidence records. Source identity, version hashes and spans are returned where available. Ambiguous exact spans remain null.

The deterministic path uses lexical retrieval and inspectable ranking signals. It does not require a generative model or guarantee semantic entailment.

Two ways to bring memory into a task.

Direct retrieval

Your application submits a query, TESSERA retrieves evidence, and your agent decides how to use it. Use the engine’s retrieve_context(), CLI tessera query, or MCP query_memories(). This is the deterministic path.

Question→Evidence→Your agent’s reasoning

Optional assisted orchestration

TesseraOrchestrator adds three prompt-based LLM stages around retrieval. These are specialized reasoning steps, not three independent autonomous workers.

  1. Information-Need Agent

    Interprets which historical facts, preferences or procedures the task depends on.

  2. Retrieval Planner Agent

    Rewrites that need into a search query. Deterministic keyword rules select drawers, falling back to all three when no subset is recognized.

  3. TESSERA retrieval

    Searches the selected stores and ranks their results. If the rewritten query finds nothing, it tries the original task instruction.

  4. State Inference Agent

    Builds an assisted context summary from the retrieved notes. The result also retains raw_memories. When there are no retrieved notes, no inference LLM call is made.

This integration wrapper requires an application-owned callable with the signature (system_prompt, user_prompt) -> str. Your application configures the model and handles its credentials and cost.

from tessera import TesseraOrchestrator

def prepare_context(engine, task, llm_fn):
    pipeline = TesseraOrchestrator(engine, llm_fn=llm_fn)
    return pipeline.run(task, top_n=3)

# Supply your own llm_fn when calling prepare_context.
# The result has consolidated_context and raw_memories.
A summary is not source evidence.

This existing assisted path is optional. Its generated context has no machine-checked grounding envelope, and recency alone cannot establish that a note supersedes another. The consuming agent still owns the final response.

TesseraTaskHook.on_task_start() can build the index and call this pipeline when your application invokes the hook. You wire it into task dispatch; installing TESSERA does not intercept another agent’s tasks automatically.

Bring something back from the task.

An Episode gives a memory three parts: the beginning (context), middle (what happened), and end (the outcome or lesson). It is a structure for a note, not a fourth semantic drawer.

from tessera import Episode, STORE_INSIGHTS

episode = Episode(
    beginning="The database service would not start.",
    middle="The team found port 5432 already in use.",
    end="Check whether port 5432 is free before starting the database.",
)
engine.write_episode(
    mem_id="operations/port-check", store=STORE_INSIGHTS,
    episode_id="deployment", episode=episode,
)
engine.build_index()

This continues the earlier Python example with its engine. For explicit task-end recording, TesseraTaskHook.on_task_end() accepts a selected drawer and a summary or episode.

Optional decomposition

on_task_end_auto() is an explicitly invoked alternative that decomposes an episode into typed notes. With llm_fn, it can use assisted extraction. Without a provider, or after supported provider/format failures, it uses a deterministic line classifier on the episode’s ending.

The fallback relies on fixed, predominantly Portuguese keyword cues. It is a heuristic, not general semantic understanding. No category is guaranteed to produce a note. decompose_episode_result() exposes the mode and fallback reason without persisting the candidates.

Proposed note→Write gate→Accepted Markdown

Every proposed write follows path validation, detection, optional transformation and admission before persistence. Review or rejection does not persist that candidate. This gate is a narrow deterministic check, not comprehensive protection against every unsafe instruction.

Sources: Decomposition modes, Write-gate contract

Choose the interface that fits.

Python
Use TesseraEngine to write, index and retrieve. Choose typed writers for intent, or write_memory_note_result() for structured admission and persistence outcomes.
CLI
tessera init, tessera write, tessera index and tessera query cover the direct workflow. Inspect the effective configuration with tessera config show.
MCP
The optional MCP extra provides tessera-mcp. Direct query_memories() retains the structured engine contract. write_memory() returns admission and persistence details, then rebuilds the index after successful persistence.

Install the MCP extra from the same repository source:

python -m pip install "tessera[mcp] @ git+https://github.com/LuigiFerronatto/TESSERA.git"

Configure your MCP client to launch tessera-mcp and set TESSERA_STORAGE_DIR to your absolute memory-store path. The variable selects the store; it does not automatically include arbitrary project sources. Client configuration formats differ, so use your client’s server registration format.

The MCP query_store() helper returns a smaller projection than query_memories(). Use the latter when you need the full evidence contract.

Sources: MCP interfaces, Package extras and entry points

Know the current boundaries.

  • Markdown is the canonical writable format. Source-code indexing is not the primary memory model.
  • Relevance is not truth, confidence, source authority or temporal validity.
  • Full supersession, temporal state keys and evidence arbitration are planned capabilities.
  • The homepage walkthrough uses fictional, fixed examples. It runs neither the TESSERA engine nor a live model.
  • Direct retrieval and optional assisted synthesis have different responsibilities. Generated context does not replace source evidence.
